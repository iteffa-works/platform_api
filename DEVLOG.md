### Ядро Flowaxy, розширення й плагіни

- `core/` → **`flowaxy/`** — ядро-фреймворк без залежностей від застосунку (готуємо до npm-пакетів): `HttpError` і fs-хелпери — в ядрі (`shared` реекспортує), БД — зі змінних `DB_*`, теки застосунку — через `configure()` (`paths.ts`); окрема перевірка `tsconfig.flowaxy.json`.
- `modules/` прибрано: **розширення** `extensions/` — `ui`, `plugins` (завжди діють); **плагіни** `plugins/` — activity, admin, auth, billing, cabinet, client-api, notifications (+ hosting), усі вимикаються. Види: `extension` / `plugin` (було `core` / `addon`).
- Розширення звертаються до auth лише через порт `access` (додано `permissionsOf`, `sessionPermissions`); порти знають власника — вимкнений плагін → 503; `registered()` — для декларацій (типи сповіщень).
- Міграція `20261119-02`: колишні модулі лишаються увімкненими (dev-сервер записав їх вимкненими під час переносу); збій `init` плагіна більше не зупиняє API.
- CLI міграцій — `src/cli/migrate.ts` (застосунок), `npm run dev` стежить за `extensions` і `flowaxy`.

### Хостинг: ізоляція плагіна, копія даних панелей, адмінка керування

- **Порти платформи** (`core/services`): `wallet`, `users`, `access`, `notifications` — контракти в ядрі, реалізації реєструють billing / auth / notifications. Хостинг більше не імпортує `modules/*` (лише порти, хуки, core, shared); гроші — `shared/money`.
- **Копія даних панелей** (`hosting_resources`) + `SyncService`: раз на 10 хв сервер за прохід (один запит на розділ для всіх власників), після змін у кабінеті — розділ власника. У БД — лише змінене (hash), стан сервера (`syncedAt` / `syncError`) і IP з панелі (лише публічні).
- Кабінет читає ресурси з БД (1–3 мс замість запиту до панелі); зміни — панель → копія → хук. `PanelService` (консоль) → `ResourceService` (акаунт).
- **Адмінка** — керування, а не копія кабінету: консоль ресурсів прибрано; сторінка сервера (огляд і синхронізація, користувачі панелі з привʼязкою, налаштування), нова картка акаунта. Огляд — `GROUP BY` / `SUM` замість 5 запитів.
- Хелпери: `domain/input.ts` (ввід форм), `http/guards.ts` (`json` / `created`), `settle`; прибрано 39 невикористаних ключів перекладу й дубль `usagePercent`.
- Web: кеш сторінок (stale-while-revalidate), індикатор завантаження; редизайн кабінету й форми замовлення (колонка підсумку).
- **Sandbox прибрано**: робоча панель — живий ISPmanager; разом із провайдером — `hosting:demo` і його дані (`data/hosting-sandbox`). Сервер з невідомим провайдером не ламає синхронізацію інших (лише `syncError`).

### Server-driven UI: плагіни лише в API

- Плагін описує інтерфейс у `plugin.ui` (сторінки, меню, сервіси, переклади); сторінка — `render(ctx)` → дерево вузлів з даними (`core/ui/schema.ts`). Тексти перекладає сервер мовою запиту.
- Модуль `ui`: `GET /ui/manifest`, `POST /ui/page`. Дії кнопок і форм — REST-маршрути плагіна (права там же); живі форми перерендерюють сторінку з `state`.

### Система плагінів і ISPmanager 6 Host

- **Addon-плагіни**: `api/src/plugins/<name>` + `web/src/plugins/<name>` з однаковим `name`. Вмикаються в `/admin/plugins` без перезапуску: маршрути за «воротами» (вимкнено → 404), події теж; стан — `plugin_states` + кеш. Новий addon — вимкнений.

## 2026-11-13

### Сесії, безпека й кабінет повністю

- **Серверні сесії** замість JWT: токен у httpOnly-cookie, у БД — SHA-256. Відкликання: вихід, «завершити сесію», зміна пароля завершує всі інші. `jsonwebtoken` прибрано.
- **CSRF** — заголовок `X-Requested-With` для змінюючих запитів; CORS лише для Client API.
- **Ліміти** на вхід (IP + email) і код 2FA; `trust proxy` для реального IP за Nginx.
- **2FA** (TOTP без бібліотек, перевірено векторами RFC 6238) + коди відновлення; вхід у два кроки.
- **Аватари**: завантаження сирим тілом запиту, тип за сигнатурою, без SVG.
- **Журнал дій** (`activity`) і **сповіщення** (`notifications`) — окремі модулі, що слухають подію `activity`; інші модулі про них не знають.
- **Білінг** (`billing`): тарифи, баланс у копійках, журнал операцій; поповнення — адміністратором.
- **Реферали**: код у кожного (наявним — у міграції), реєстрація за `?ref=`, список запрошених.
- **Антифішинговий код** зберігається в налаштуваннях.
- **i18n uk / en / ru**: інтерфейс (типізовані ключі), повідомлення API (`Accept-Language`), тексти журналу й сповіщень, назви системних ролей. Мова — як тема: cookie + акаунт.
- **Кабінет**: вкладки Акаунт · Безпека · Налаштування · Тариф · Реферали · Журнал · Доступи, сторінка сповіщень, у шапці — мова, баланс, дзвіночок.
- **Адмінка**: Білінг, Журнал дій.
- **Чернетки міграцій** `*.draft.ts` (`MIGRATIONS_DRAFTS=1`): розробка схеми на тестовій БД, не чіпаючи робочу.

Перевірено: 66 сценаріїв API (сесії, CSRF, ліміти, 2FA, аватар, реферали, білінг, журнал, сповіщення, i18n), міграції 05–09 поверх наявних даних з відкатом, UI трьома мовами й темами.

## Відомі обмеження

- **Листи не надсилаються** — немає поштового модуля: не працюють підтвердження email, відновлення пароля, антифішинговий код у листах.
- **Зміна email** — після підтвердження пошти.
- **Оплата** — платіжного шлюзу немає, рекурентних списань немає (тариф — разове списання при переході).
- **Ліміти й черга Client API — у памʼяті процесу**; для кількох інстансів — Redis / БД.
- **Client API** — один спільний ключ із `.env`; потрібні персональні ключі користувачів (див. наступні кроки).
- **Повідомлення API з підставленими значеннями** (назви ресурсів тощо) не перекладаються.
- **Назви власних ролей і тарифів** — як ввели в адмінці (не перекладаються).
- **Захищені сторінки рендеряться в браузері** (SSR — лише оболонка).

## Наступні кроки

1. Поштовий модуль (Mailhog локально): підтвердження email, відновлення пароля, антифішинговий код у листах.
2. Client API: персональні API-ключі в кабінеті (права ключа ⊆ права ролі), `req.actor`, ліміт на ключ; маршрути плагіна для обох контурів.
3. Передача ролі розробника з UI; «роль за замовчуванням» як налаштування.
4. Платіжний шлюз і рекурентні списання.
