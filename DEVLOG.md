## 2026-11-15

### Кабінет клієнта хостингу й демо-дані

- Картка акаунта з вкладками: швидкий старт, сайти, DNS, пошта, БД, FTP, SSL, cron, налаштування — ті самі розділи, що в консолі адміністратора (`ui/sections` + `PanelScope`), власник зафіксований сервером.
- REST `/cabinet/hosting/:id/panel/*`: owner з запиту ігнорується, DNS-записи лише власних зон, Sandbox поважає власника при видаленні; дії клієнта — `hosting.panel_changed` у його журналі.
- `npm run hosting:demo -w api` — демо-сервери Sandbox (UA / DE), тарифи, три акаунти в різних станах.


### Хуки, ООП-плагін хостингу, повна консоль ISPmanager, Sandbox

- **Хуки й фільтри** (`core/hooks`): `addAction / doAction`, `addFilter / applyFilters`, пріоритети, ізоляція помилок, умова `when`, типи через declaration merging. `core/events` — аліас.
- **Хостинг — еталон плагіна**: `module.ts` (корінь композиції) + класи-сервіси (Server / Plan / Account / Order / Panel / Lifecycle), `domain/`, `providers/`, `http/`, `ui/`, `hooks.ts`. Журнал і сповіщення — підписники хуків; ціна — фільтр `hosting.order.price`.
- **Провайдери**: контракт `PanelClient` (accounts, sites, dns, mail, databases, ftp, ssl, cron, system). ISPmanager 6 — транспорт + клас на розділ; **Sandbox** — технічна панель у памʼяті / JSON з демо-даними й симуляцією збоїв.
- **Консоль панелі** в адмінці: огляд (система, ліцензія, служби, IP, PHP), користувачі, сайти, DNS-зони й записи, пошта, БД, FTP, SSL, cron, налаштування. Огляд хостингу з KPI.
- **Server-driven UI**: вузли `stats`, `menu`, `breadcrumbs`, `progress`, модальні вікна (`button.dialog`), дії в шапці панелі, пошук у таблицях, фільтри через URL; плоский стиль адмінки.
- Перевірено на реальній панелі ISPmanager 6.155 (`isp.flowaxy.com`): усі розділи, створення / видалення тестових обʼєктів; знайдено й виправлено: у `su`-режимі немає колонки owner, поштовий домен потребує конкретної IP.


### Server-driven UI: плагіни лише в API

- Плагін описує інтерфейс у `plugin.ui` (сторінки, меню, сервіси, переклади); сторінка — `render(ctx)` → дерево вузлів з даними (`core/ui/schema.ts`). Тексти перекладає сервер мовою запиту.
- Модуль `ui`: `GET /ui/manifest`, `POST /ui/page`. Дії кнопок і форм — REST-маршрути плагіна (права там же); живі форми перерендерюють сторінку з `state`.
- Web: `constructor/remote` — маніфест, `RemotePage`, `UiNode`, `UiForm`; `web/src/plugins` прибрано, `Flag` / `Ring` — у UI-kit. Новий плагін не потребує змін у web.
- Хостинг переписано на схему: список, замовлення, картка, адмінка (акаунти, тарифи, сервери).

Перевірено: 23 сценарії рендеру (маніфест гостя / користувача, uk / en, усі 6 сторінок на даних, жива форма, 404 для чужого й вимкненого), svelte-check, typecheck, тести, збірка.

- **Фонове завдання**: нагадування, автопродовження, блокування за несплату й розблокування після оплати, відновлення завислих замовлень, синхронізація диска / сайтів.

- **Безпека**: ліміти й ексклюзивність операцій, крипто-паролі, заборонені системні імена, маски в діагностиці, підтвердження видалення; рекомендації для панелі — [docs/plugins/hosting.md](docs/plugins/hosting.md).

### Система плагінів і ISPmanager 6 Host

- **Addon-плагіни**: `api/src/plugins/<name>` + `web/src/plugins/<name>` з однаковим `name`. Вмикаються в `/admin/plugins` без перезапуску: маршрути за «воротами» (вимкнено → 404), події теж; стан — `plugin_states` + кеш. Новий addon — вимкнений.
- **Web**: addon підхоплюються `import.meta.glob`, вбудовуються в навігацію `admin` / `cabinet` (`section`), мають власні переклади `<плагін>:<ключ>`.
- **ISPmanager 6 Host** ([ТЗ](docs/plugins/ispmanager.md)): сервери (пароль зашифровано, перевірка зʼєднання), акаунти (створити в панелі / привʼязати наявного, блокування, видалення), кабінет — вхід у панель без пароля (`session.newkey`), сайти, зміна пароля.

## 2026-11-13

### Сесії, безпека й кабінет повністю

- **Серверні сесії** замість JWT: токен у httpOnly-cookie, у БД — SHA-256. Відкликання: вихід, «завершити сесію», зміна пароля завершує всі інші. `jsonwebtoken` прибрано.
- **CSRF** — заголовок `X-Requested-With` для змінюючих запитів; CORS лише для Client API.
- **Ліміти** на вхід (IP + email) і код 2FA; `trust proxy` для реального IP за Nginx.
- **2FA** (TOTP без бібліотек, перевірено векторами RFC 6238) + коди відновлення; вхід у два кроки.
- **Аватари**: завантаження сирим тілом запиту, тип за сигнатурою, без SVG.
- **Журнал дій** (`activity`) і **сповіщення** (`notifications`) — окремі модулі, що слухають подію `activity`; інші модулі про них не знають.
- **Білінг** (`billing`): тарифи, баланс у копійках, журнал операцій; поповнення — адміністратором.
- **Реферали**: код у кожного (наявним — у міграції), реєстрація за `?ref=`, список запрошених.
- **Антифішинговий код** зберігається в налаштуваннях.
- **i18n uk / en / ru**: інтерфейс (типізовані ключі), повідомлення API (`Accept-Language`), тексти журналу й сповіщень, назви системних ролей. Мова — як тема: cookie + акаунт.
- **Кабінет**: вкладки Акаунт · Безпека · Налаштування · Тариф · Реферали · Журнал · Доступи, сторінка сповіщень, у шапці — мова, баланс, дзвіночок.
- **Адмінка**: Білінг, Журнал дій.
- **Чернетки міграцій** `*.draft.ts` (`MIGRATIONS_DRAFTS=1`): розробка схеми на тестовій БД, не чіпаючи робочу.

Перевірено: 66 сценаріїв API (сесії, CSRF, ліміти, 2FA, аватар, реферали, білінг, журнал, сповіщення, i18n), міграції 05–09 поверх наявних даних з відкатом, UI трьома мовами й темами.

### Кабінет за референсом, тема, INT-ідентифікатори

- Тема світла / темна: cookie (SSR без мерехтіння) + `user_preferences`.
- Редизайн: кабінет (шапка-картка, меню сервісів і акаунта), адмінка (темна смуга, бічне меню з пошуком).
- `id` усіх таблиць — `INT UNSIGNED AUTO_INCREMENT` (міграції переписано до першого деплою).
- Плагіни web: `site`, `auth`, `cabinet`, `admin` — сторінки, блоки й навігація оголошуються в плагіні.

### Ролі й рівні прав

## Відомі обмеження

- **Листи не надсилаються** — немає поштового модуля: не працюють підтвердження email, відновлення пароля, антифішинговий код у листах.
- **Зміна email** — після підтвердження пошти.
- **Оплата** — платіжного шлюзу немає, рекурентних списань немає (тариф — разове списання при переході).
- **Ліміти й черга Client API — у памʼяті процесу**; для кількох інстансів — Redis / БД.
- **Client API** — один спільний ключ із `.env`; потрібні персональні ключі користувачів (див. наступні кроки).
- **Повідомлення API з підставленими значеннями** (назви ресурсів тощо) не перекладаються.
- **Назви власних ролей і тарифів** — як ввели в адмінці (не перекладаються).
- **Захищені сторінки рендеряться в браузері** (SSR — лише оболонка).

## Наступні кроки

1. Поштовий модуль (Mailhog локально): підтвердження email, відновлення пароля, антифішинговий код у листах.
2. Client API: персональні API-ключі в кабінеті (права ключа ⊆ права ролі), `req.actor`, ліміт на ключ; маршрути плагіна для обох контурів.
3. Передача ролі розробника з UI; «роль за замовчуванням» як налаштування.
4. Платіжний шлюз і рекурентні списання.
