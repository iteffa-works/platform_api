# План: ролі й рівні прав

Мета — одна вбудована роль **розробника** (власник платформи) і конструктор ролей в адмінці:
нові ролі збираються з рівнів прав **без змін у коді**.

---

## Статус

Етапи 1–2 реалізовано: ролі в БД, рівні прав, `requirePermission`, міграції, web на `can()`.
Етап 3 — простий UI ролей в адмінці (`/admin/roles`); лишились налаштування ролі за замовчуванням і передача ролі розробника.

## Цільова модель

### Ресурси й рівні (каталог у коді)

Перевірки прав виконує код, тому **перелік ресурсів оголошують модулі**.
Кожен ресурс має впорядковані рівні:

```
none < view < edit < manage
```

| Рівень | Значення |
|--------|----------|
| `none` | доступу немає |
| `view` | бачити |
| `edit` | змінювати |
| `manage` | змінювати + налаштовувати / видаляти / роздавати |

Модуль оголошує свої ресурси поруч із плагіном — новий модуль сам додає їх у каталог:

```ts
export const plugin: Plugin = {
  name: 'admin',
  permissions: {
    'admin.panel': { label: 'Адмінка', levels: ['view'] },
    users:         { label: 'Користувачі', levels: ['view', 'edit', 'manage'] },
    roles:         { label: 'Ролі', levels: ['view', 'manage'] },
  },
  routes: adminRoutes,
};
```

Стартовий каталог: `admin.panel`, `users`, `roles`, `settings`.

### Ролі (дані в БД, редагуються в адмінці)

Роль — це назва + набір «ресурс → рівень». Код ролей не знає, лише перевіряє рівні:

```json
{ "slug": "support", "name": "Підтримка",
  "permissions": { "admin.panel": "view", "users": "view" } }
```

| Роль | Тип | Права | Редагується | Видаляється |
|------|-----|-------|-------------|-------------|
| `developer` | системна | усі (`*`) | ні | ні |
| `user` | системна | базові (кабінет) | так, права | ні |
| будь-які інші | створені в адмінці | зібрані з рівнів | так | так |

### Користувач

- Одна роль на користувача (`users.roleId`). Кілька ролей — лише якщо знадобиться.
- Права обчислюються на сервері на кожен запит. JWT містить лише `sub`, тож зміна ролі діє одразу, без перевипуску токена.

---

## Акаунт розробника

- `developer` має **рівно один** акаунт — перший зареєстрований.
- Має всі права, зокрема на ресурси майбутніх модулів (wildcard `*`).
- Адмінка не може: змінити йому роль, видалити його, видати роль `developer` іншому.
- Передача ролі — окремою дією самого розробника, з паролем (розробник → вибраний користувач, сам переходить у вказану роль).
- Аварійне відновлення — CLI-скриптом на сервері (`npm run -w api roles:set-developer <email>`), не через UI.

---

## Правила безпеки

1. **Без ескалації**: користувач з `roles: manage` не може створити роль або видати права вищі за власні.
2. Не можна змінити власну роль.
3. Роль, на якій є користувачі, видаляється лише з переназначенням їх на іншу роль.
4. Роль за замовчуванням для реєстрації — налаштування в адмінці (стартово `user`), не можна поставити `developer`.
5. Каталог прав з API — джерело правди; невідомі ключі в ролі ігноруються, рівень вище дозволеного для ресурсу відхиляється.
6. Усі зміни ролей і призначень пишуться в audit log (Хвиля A, Identity).

## API

| Метод | Шлях | Право |
|-------|------|-------|
| `GET` | `/auth/me` | сесія; повертає `role { key, name }` + `permissions` |
| `GET` | `/admin/permissions` | `roles: view` — каталог ресурсів і рівнів |
| `GET` | `/admin/roles` | `roles: view` |
| `POST` | `/admin/roles` | `roles: manage` |
| `PATCH` | `/admin/roles/:id` | `roles: manage` |
| `DELETE` | `/admin/roles/:id` | `roles: manage`, тіло `{ reassignTo }` |
| `GET` | `/admin/users` | `users: view` |
| `PATCH` | `/admin/users/:id` | `users: manage`, тіло `{ roleId }` |
| `POST` | `/admin/developer/transfer` | лише `developer` + пароль |

Перевірка в маршрутах замість `requireAdmin`:

```ts
router.get('/admin/users', requirePermission('users', 'view'), …);
```

## Web

- `user` у store отримує `permissions`; хелпер `can('users', 'edit')`.
- Сторінки конструктора: `access: 'public' | 'user'` + необовʼязкове `permission: ['admin.panel', 'view']` замість `access: 'admin'`.
- `Topbar`, `AdminLinkBlock`, підпис у кабінеті — через `can(...)` і `role.name`, без порівнянь з `'admin'`.

## Критерії готовності

- Нова роль створюється й призначається в адмінці — жодного коміту в код.
- Новий модуль додає свої ресурси оголошенням у `plugin.permissions` — вони одразу зʼявляються в матриці.
- `developer` неможливо змінити, видалити чи продублювати через API.
- Користувач не може видати права вищі за власні.
- Зміна ролі діє з наступного запиту.

## Рішення за замовчуванням (можна переглянути)

1. Базова роль нових реєстрацій — `user` («Користувач»).
2. Розробника в списку користувачів бачать усі з доступом до адмінки (змінити його не може ніхто).
3. Одна роль на користувача.
